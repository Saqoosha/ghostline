# HDZero の DVR から飛行経路を 3DGS 上に復元する

ゴーグルの DVR（`hdz_0067.ts`、1280×720 60 fps HEVC、有効画は中央 960×720 の魚眼、OSD は上 82 px と
下 88 px）だけから、同じ場所の 3DGS スキャン（JDL-2026-R6）上でドローンのカメラ姿勢を全フレーム求め、
web ビューアで 3DGS の描画と DVR を重ねて確かめる。スキャン側の準備（Avata 2 の SfM、ゲートの
貼り間違いの修正、GPS で実スケール）は memory の `jdl-2026-r6-scene` にある。ここは DVR 側の通しと、
高くついた罠。数字は全部 hdz_0067（94.6 s、5,676 フレーム）の実測。細かい試行の記録は
[dvr-refinement-log.md](dvr-refinement-log.md)（英語のラボノート）。

道具は `tools/dvr/`。GPU の仕事は win4090（WSL の `~/gsenv`、gsplat 1.5.3、RTX 4090）、
COLMAP は win4090 の `~/COLMAP/COLMAP-3.12.6-windows-cuda`。長い仕事は**スケジュールタスクで**回す
（`regtask-*.ps1`。ssh から直接起動した WSL のプロセスはセッションと一緒に死ぬ）。**他のセッションが
`wsl --shutdown` すると走っている refine も黙って死ぬ**（ログは途切れるだけ）。`refine_batch.py` は出力の
jsonl にある枚を飛ばすので、`rm -f` 無しで同じタスクを起動すれば続きから。重複した記録は
`refined2poses.py` が最後を採る。

## 通し

| 工程 | 道具 | 時間（95 s のフライト） |
|---|---|---|
| .ts から魚眼→100° ピンホール動画 `dvr_pinhole.mp4` ＋ sidecar json | `undistort.py` | 数分 |
| COLMAP 登録（`OPENCV_FISHEYE`、`camera_mask_path` で OSD を隠す、位置を知っているペアだけ照合） | `dvr4.ps1` | 抽出 1 分、照合 40 分（ペア数に比例。70 万組で 27 分）、登録は秒 |
| 空白を LK で埋める（登録済みフレームの 2D-3D 対応点を隣のフレームへ追って PnP） | `gapfill.py` | 数分 |
| 経路の解決（同一アーチの取り違え、速度の壁、Kalman。観測は inliers で重み付け） | `resolve.py` | 秒 |
| 60 fps の全フレームに補間（格子 Kalman + RTS、観測は inliers で重み付け、向きは COLMAP フレーム間の slerp） | `interp60.py` | 秒 |
| 3DGS との画素比較で姿勢を詰める | `refine_batch.py` → `refined2poses.py` | **0.44 s/枚**、全フレームで 40 分 |
| **描画と MASt3R の照合で姿勢を取り直す（CPR、下の節）** | `cpr_all.sh`（`cpr_render.py` → `cpr_match.py` → `cpr_fuse.py` を 2 周、3 周目は穴埋めのフレームだけ） | 全フレームで約 2 時間 |
| ビューアで確認 | `viewer/`（Vite + PlayCanvas） | — |
| 外れは人が印を打つ → 解く → 変わった分を refine（**CPR とは別の系統**：`marks_apply.sh` は run 10 から解き直し、CPR の結果は入らない） | viewer の `mark`、`marks_apply.sh`、`marks_solve.py` | 1 周 1 時間の打ち込み、解くのは秒、refine 数分 |

**合計 1〜2 時間（CPR を足すとさらに約 2 時間）、ほとんど GPU の放置。** 人が触るのは最初の 20 分。ただし**同じスキャン、同じコース配置**
のときだけ。今回はフラッグが撮影日と違う位置にあり、その周りは refine が合わせに行けない。

## 印も COLMAP も使わない通し（FDF CUP R6 で 6 本）

DVR・スキャンの撮影カメラ（`scan_cameras.json`）・3DGS の ply だけで回る。上の表の系統より新しく、**他の DVR ではこちらを使う**。

```bash
[FPS=30] T0=<s> DUR=<s> tools/dvr/dvr_pipeline.sh <dvr.ts|mp4> <name> <scan_cameras.json> </mnt/c/... の ply>
bash tools/dvr/refine_all.sh <name> ...        # win4090 の WSL 側。各飛行の `done` を待って refine_flight.sh
```

1. `undistort.py` → `cpr_track.py`（撮影カメラの描画から DINOv2 で再局在化し、等速の予測で描いて MASt3R + PnP で 1 フレームずつ）
   → `cpr_ba.py`（照合点の再投影と動きの制約を全フレーム同時に解く）→ `takeoff.py`
2. `refine_flight.sh`：解いた姿勢で描き直して照合し直す（`cpr_rematch.py`、2 周目）→ 両周の照合で `cpr_ba.py` → `takeoff.py`。
   `eval_align.py` で 1 周目と比べ、良いほうを `poses60.json` に置いて理由を `choice.txt` に書く
3. 済んだ飛行の束調整だけやり直すのは `rebundle.sh <name>`（追跡の照合は win4090 に残っている）

**人が見る「ずれ」の正体は、近い点だけで決まった姿勢。** 芝の上では数千の近い点が RANSAC の合意を作り、遠い電柱や木の数十点は
その姿勢と 15〜20 px 食い違うので**正しいほうが外れとして捨てられる**。近い点だけでは位置の誤差を向きの誤差で打ち消せるので、
近いアーチは合ったまま遠くだけずれる（d05 #293）。レンズの校正は原因ではなかった（端でのかたより 0.7 px、焦点距離を 0.8〜1.2 倍に
振って PnP の inlier が最大になるのは 1.00 倍）。直し方は 3 つで、どれも入っている：
- `cpr_track.py` は RANSAC の判定（`inl`）付きで全部の照合をダンプに残す
- `cpr_ba.py` は 1 フレーム 300 点を距離帯（5 / 15 / 40 m）で等分して取り、15 m 以遠は RANSAC に捨てられた点も使う
- 2 周目の照合。解いた姿勢から描けば遠景が近い位置に来て照合できる。**これが本体**：d05 で遠い点が 10 px 超のフレーム 67 → 27
  （距離の等分だけでは 55）。3 周目は 23 で頭打ちなので、通しは 2 周目まで

**動きの制約は加速度ではなくジャーク**（`SIG_JERK` 300 m/s³、加速度 40、角加速度 50、`GATE` 1000）。60 fps では 1.5 cm の揺れが
約 100 m/s² の加速度に見え、レース機の本物の機動（30 m/s² 前後）より大きい。だから加速度を 15 に絞ると離陸や旋回の正しい照合が外され
（d05 で解けたフレーム 4,518 → 4,061、離陸直後の最初の解が #161 → #179）、加速度に Huber を掛けると揺れを通す（揺れ 1.45 → 1.59 cm）。
ジャークなら揺れは数万 m/s³、機動は約 150 m/s³ で分かれる。揺れ（0.25 s の局所当てはめからの距離）は d05 で p50 1.45 → 0.60 cm、
元の経路からの移動は p50 1.4 cm、500 °/s 超の旋回でも 3〜7 cm。数字の全部は `cpr_ba.py` の冒頭。

**束調整は正しい照合を捨てることがある。** 判定（`GATE` 1000）はフレーム自身の点の回転の情報で重み付けするので、
300 点なら**向きが約 1° ずれるだけで落ちる**。落ちたフレームは二度と戻らず、隣が支えを失って次の回でまた落ちる。KNT で踏んだ形が 3 つあり、
どれも `cpr_ba.py` の既定で直してある（`DEBUG=a:b` でその範囲の判定の内訳が出る）：
- **出発点が短い弧の補間**（`INIT_OBS`）。前の解の穴は近道の slerp で、約 270° 回る旋回を逆回りに描いていた。1,200〜3,200 点で解けた
  #370〜#395 が 75° ずれた出発点と比べられて全部落ちた。点のあるフレームは自分の答えから始める → #368〜#394 が 0 → 21 / 27
- **k が測れない答えを信用しない**（`K_NONE` 0.5、前は位置の重み 0.0004）。速い回転では k の試験（視点を 2 m ずらして解き直す）が
  失敗しやすく、KNT で 11%（d05 6%）。位置が動きの制約だけで 1〜3 m 流れ、向きが帳尻を合わせてねじれて落ちた
  （自分の点で 18〜21 px、照合の答えなら 3〜6 px）→ #858〜#882 が 0 → 16 / 25
- **角加速度は Huber**（`HUBER_ALPHA` 1σ）。blackbox の角加速度は 30 fps 間隔で p90 44・p99 272・最大 1,533 rad/s²、KNT は 2 フレームで
  55 → 760 °/s。照合の回転の揺れは数 rad/s² しかないので、位置と違って大きな値を通しても揺れは入らない。単独では KNT に効かなかった
d05 では 3 つとも入れて遠景 23 / 145 は同じ、切り返し（blackbox の角加速度 100 rad/s² 超）でのジャイロとの差 p50 245 → 203 °/s。
ただし blackbox の加速度との差は z で 11.9 → 12.3 m/s² とわずかに悪い。

**離陸（`takeoff.py`）。** スタート台の上では追跡がほとんど効かず、束調整は離陸後の動きを過去へ直線で延ばす（d05 で最大 31 m 漂い、
1 枚だけ解けた #24 は似た景色への取り違えで 35 m 外れていた）。離陸は画の隣接差分が床の 2.5 倍を 0.5 s 超えた最初のフレーム
（d05 #154、blackbox のスロットルは #150）。台の位置は、解けたフレームが 10 枚続く区間の最初から 0.6 s に「止まった状態から出る
3 次」を当てはめて戻し、最後の 15 フレームで解へ移す。1 枚の解けたフレームにつなぐと、そこが外れのとき逆戻りのフックが、
位置と速度に合わせてもそのフレームの揺れを拾って S 字が出た（blackbox で横の加速度は 0〜2 m/s²、経路からの予測は ±55 → 5）。

**台は人が置くほうが正しい。** 当てはめは離陸後の飛行から逆に延ばすだけなので、KNT は 5.2 m 外れ、#0 を描くと別の場所を見下ろしていた。
ビューアの `pad`（下）で DVR の最初のフレームに描画を重ねると `<flight>/pad.json` に保存され、`takeoff.py` は台をそこに固定して
曲線もそこから出す（台と最初の解の間は向きを smoothstep で移す。止めたままだと KNT で 35° が 1 フレームに出た）。ぼかした画素の差
（#0、小さいほど DVR に近い）で、人の台が当てはめに勝ったのは KNT 0.866 → 0.563・SENA 0.696 → 0.550・d05 0.635 → 0.513・d07 0.559 → 0.507。
SAQOOSHA は同じ（0.541 / 0.547）、**e02 は当てはめのほうが近い**（0.486 / 0.559）ので `pad.json` を消した。人の台を MASt3R で詰める
`pad_refine.py` は勝てなかった（KNT で 0.564 → 0.571。位置は描いた場所へ毎回 4〜32 cm 流れ、形式上の標準偏差は 1 mm と出てこの偏りを見ない）。

**物差し（`eval_align.py`）。** 解いた姿勢で描いて DVR と MASt3R で照合し、照合点の画素のずれを奥行き別に出す。芝は同じ画素どうしが
対応しがちで近い帯は甘く出るので、**判定は 15 m 以遠**。値は 512 幅の描画の画素単位（元の 1.9 px）で刻まれる。
`frame_compare.py` は 1 フレームの DVR・描画・alpha・重ねを並べる。

**照合の描画は、ゲームと web と同じ規則で描く（`frustum.py`）。** gsplat は近平面より前の splat を全部描くので、カメラのほぼ真横にある
3〜60 cm の splat が透視投影で σ 数千〜数百万 px に伸び、空と遠景を灰色に塗っていた（d05 #1435：空が 108、PlayCanvas は 215〜230、
DVR は 170〜176）。mod（`SplatUtilities.compute` の `_CullCenterSlack`）と web は中心が視野の 1.2 倍より外の splat を描かないので、照合の
7 か所（`cpr_track` / `cpr_rematch` / `gap_track` / `eval_align` / `frame_compare` / `pad_refine` / `color_fit`）も `rasterize_culled` で
同じにした（`CULL`、0 で元どおり）。PlayCanvas の絵との差は 24.3 → 10.0。gsplat 1.5.3 は不透明度を視点ごとに受けないので、1 視点ずつ描く。
**SH の次数・アンチエイリアス・小さい splat の足切り・SOG の圧縮は原因ではなかった**（どれも空の色が動かない）。

**シーンの色も照合を変える。** d07 を同じコードで、元の色と Saqoosha が SuperSplat で直した色で解くと、追跡 683 → 851 フレーム、遠景 10 px 超
12 → 7（どちらの ply で測っても同じ向き）。`color_fit.py` は解けたフレームで描画と DVR の色の分布（平均と共分散）を合わせる線形変換を当て、
SH ごと焼く。画素の最小二乗はずれた対に引かれてコントラストを潰す（利得 0.37、負の対角）ので使わない。濁った描画で当てた変換は強すぎた
（利得 1.4〜1.9）ので、上の修正の後に当て直した（1.1〜1.3、`FDF-2026-R6b-spirula-web-dvr2`）。d07 の比較（遠景は直した描画 ＋ dvr2 で測る）：

| | 1 周目の描画 / 色 | 2 周目の描画 / 色 | 自分の点で解けた | うち k > 0.5 | 遠景 >10 / >5 px（80 中） |
|---|---|---|---|---|---|
| d07c | 全部描く / 直した色 | 同じ | 827 | 359 | 6 / 16 |
| d07kd | 1.5 倍で切る / dvr2 | 同じ | 616 | 51 | 4 / 17 |
| d07m | 全部描く / 直した色 | 1.5 倍で切る / dvr2 | **830** | 365 | **4 / 17** |

切ると追跡は途切れやすく（851 → 598〜648）、答えは正直になる（位置が描いた場所をなぞる k > 0.5 が 359 → 28〜51）。**1 周目で数を拾い、
2 周目を切った描画で取り直す d07m** が両方を取った。

**レースの 4 分割動画。** 1 マス 640×360 は HDZero の 4:3（960×720）を横に引き伸ばしたもの。横を 3/4 に縮めて 1280×720 の中央に
置けば DVR と同じ形になる（`crop=640:360:X:Y,scale=960:720,pad=1280:720:160:0`）。30 fps なので `FPS=30`。墜落の後は映像が
灰色になり、追跡は `interp` で持ち越すだけなので、`eval_align.py` と `cpr_rematch.py` は `ba` / `ba-fill` / `takeoff` のフレームしか扱わない。

| 飛行（FDF R6b） | 遠い点が 10 px 超 / 5 px 超のフレーム（1 周目 → 2 周目 → いまの `poses60_pad.json`） | 備考 |
|---|---|---|
| d05 | 67 → 23 → 23 / 145（534 中） | 3 周目 |
| d07 | 14 → 8 / 23 → 5 / 20（80 中） | |
| e02 | 33 → 23 / 55 → 7 / 41（181 中） | 台は当てはめのまま（下） |
| レース SAQOOSHA | 34 → 12 / 32 → 12 / 28（93 中） | 解像度が半分、30 fps |
| レース SENA | 55 → 29 / 65 → 25 / 59（212 中） | |
| レース KNT | 61 → 47 → 46 / 79（165 中） | 速さのせい（下）。穴埋めの再追跡込み |

評価は解けたフレームを 10 枚おきに取るので、解けるフレームが増えると母集団も変わる（d07・e02）。

**ローリングシャッターは効くが、既定では切ってある。** カメラは上から下へ約 3 ms で読む（上 3 分の 1 と下 3 分の 1 を別々に解いた向きの差が、
回転の速さに比例して 1.2° → 3.2° に増える。束調整の `RS_READOUT` を振ると 500 °/s 超の照合の残差が最小になるのは d05・SENA・KNT とも 3 ms）。
ただ、ビューアは 1 フレームを 1 つの姿勢で描くので、読み出しを入れて解いた中央の行の姿勢は重ねたときの見た目が悪くなり
（遠くが 10 px 超のフレームが 6 本中 4 本で増えた。d05 23 → 35）、blackbox で見た経路もほぼ動かない（加速度の残差 9.8 → 9.7 m/s²）。

**KNT が合わないのは速さのせい。** 同じ回転の速さで比べると、残差は 3 人とも同じ。KNT は 500〜800 °/s にいる時間が 17%（SENA 12%、
Saqoosha 4〜5%）で、速さの 90% 点も 37.9 m/s（ほかは 30〜32）。レンズは、照合点から魚眼の校正を解き直しても KNT と SENA で同じだけしか
動かず（縦横比 1.018 と 1.019、4 分割のマスを戻すときの共通のずれ）、残差もほとんど減らない。像の円が四隅に写るのはレンズかカメラの型の
違いに見えるが、合い方には効いていない。

KNT の穴を埋めたのは 3 つ（`gap_track.py` が穴を両端から追い直し、1 周目の答えの孤立区間からも歩き出す）：
- **HDZero のブロックノイズを塗る**（`hdz_blocks.py`）。540p の送出は 720×540 の 8×8 ブロックで、ゴーグルが 4/3 倍するので録画では
  10.67 px の格子（ノイズ画像の隣接差がちょうど 32/3 px の倍数で立つのを実測）。周りの 4 ブロックと色が違い、縁の段差が内側の 2 倍を
  超えるブロックを `cv2.inpaint` で塗り、そのマスクに落ちた照合は捨てる。人のラベル付け（`label_blocks.py`）と比べても手の規則で足りた
- **照合の描画で 1 m より近い splat を描かない**（`NEAR`、`cpr_track.py` / `cpr_rematch.py` / `gap_track.py` の既定 1.0）。芝の上 0.5 m では
  スキャンの大きく薄い地面の splat が画面全体を霧にし、#380〜#388 で鉄塔も木立も消えていた。穴の中で解けたフレーム #355〜#399 が 4 → 12
- 上の束調整の 3 つ

**まだ解けない形：照合が位置を返さない区間**（KNT #1352〜#1364）。600〜2,000 点で向きは合う（補間と 0〜2°）が k が 0.97〜1.52 で、
位置は描いた場所をなぞるだけ。描画は向きが正しいので DVR に重なって見え、線だけ他の周から最大 1.8 m 外れる（`K_NONE` を変えると動く＝
どちらも測っていない）。隣接フレームの流れから進行方向を足す `flow_rel.py`（`cpr_ba.py FLOW=`）は効かなかった：d05 では向きは合う
（視差 20 px 超で p50 1.9°）が経路は動かず、race の 30 fps ではこの区間の方向がフレームごとに 80〜120° 跳ぶ。残る手は印。

**blackbox は通しに入れていない**（他のパイロットの DVR には無い）。d05 では答え合わせに使った：角速度の大きさの相関 0.944、時刻は
ペアリングの 0.1 s から 34 ms 詰まり、カメラは機体の前方向から約 49° 上向き。2 周目の照合で経路そのものが良くなったことも blackbox で確かめた
（d05：加速度の相関 y 0.53 → 0.71、z 0.88 → 0.92、残差 12.0 → 9.8 m/s²、ジャイロの残差 19.1 → 15.8 °/s）。

## CPR：描画と MASt3R の照合で、印なしに直す（2026-09-24）

GS-CPR（[arXiv 2408.11085](https://arxiv.org/abs/2408.11085)）の形。姿勢の候補から 3DGS の RGB と深度を
描き、DVR フレームと MASt3R で照合し、描画側の点を深度で 3D に上げて PnP-RANSAC を解く。
**画素比較の basin に縛られない**ので、数 m 外れた姿勢からでも戻る。調査の全体は
[research/2026-09-24-3dgs-localization.md](../research/2026-09-24-3dgs-localization.md)。

**印 537 個での再投影誤差（印は評価にだけ使い、CPR は一度も見ていない）：** 2026-09-24 に同じ `marks.json` と
`marks_eval.py` で全行を測り直した値。下の「人が打つ対応点」節の「run 10 の p50 32 px」とは一致しない（こちらは 36 個が

## refine の設定（これで固定）

```
BLUR=3 BANDS=4 BATCH=8 ITERS=16 ONLY_INTERP=1   refine_batch.py <ply> dvr_pinhole.mp4 poses60_init.json refined.jsonl 1
```

フレームごとに viewmat の左から se(3) の 6 自由度を掛けて Adam、粗→細 2 段（240×180 → 480×360）、
SH 1 次、不透明度 0.1 未満を落として 256 万 splat。損失は正規化グレーの L1 ＋ 勾配 L1 ×2、マスクは
OSD・歪み補正の縁・DVR 側で検出した空（3DGS の空は浮遊物）。prior は 6° / 1 m で二次、採用は loss が
1% 以上下がって 10° / 1.5 m 以内のとき。**毎フレーム自分の補間姿勢から始める**（前フレームの補正量を
引き継ぐと数百枚で 15〜59° 流れる。芝は姿勢を支えない）。

3 つの設定はそれぞれ測って決めた：

- **`BLUR=3`（両画像を σ 3 px でぼかす）が本体。** ぼかさない loss は向きを見ていない。#184 で yaw を
  ±6° 振ると地平線の帯の loss は 3.23〜3.39 で平ら、芝の帯は片側へ単調に下がる —— 芝（画面の 3 分の 2、
  動きブレで滲む）の差が偶然減る方向へ姿勢が流れる。σ 3 で地平線の帯は椀型、芝は平ら。同じことを
  COLMAP フレーム 40 枚で「DVR の隣のフレーム（3〜8° 違う）と比べても loss が区別できない」形でも確認した
- **`BANDS=4`（上下 4 帯の平均の平均）**：素の画素平均だと 96 枚中 66 枚で地平線の帯が悪化した
  （2.67 → 3.05）。芝の画素数で回転を決める行が負ける
- **`BATCH=8`**：gsplat は `viewmats [B,4,4]` を受ける。1 枚ずつ 2.77 s → 8 枚で 0.44 s。**16 は 24 GB を使い切って止まる**（逆伝播用の中間が
  カメラ × splat）。GPU を 2 ジョブで分けても同じ症状

結果（hdz_0067）：観測のある 5,564 枚のうち 5,109 枚が採用、補正は中央値 9 cm / 1.2°、1 m 超の段差ゼロ。

**画素比較で直せるのは数度・1 m まで。** 探索の basin は 240×180 で数 px。30° 外れた補間は、反復を増やしても
120×90 の段を足しても yaw の格子探索を前置きしても届かない（全部試した）。
**位置の格子探索（±6 m、`TSEARCH`）も駄目**。#915 では 6 m 先に真の極小があったが、全 5,564 枚に掛けると
**200 inliers 超の COLMAP アンカー 455 枚が中央値 6 m 動いて loss が 14% 下がった**。アンカーは 1 m 未満で正しいので、blur loss には 5 m 離れた
偽の極小がほぼ全フレームにある（芝の模様と同じ形のフラッグが繰り返す）。位置の探索結果はどこでも信用できない。
大きな外れは**下の 3 つ**で直す。

## 経路が外れる 3 つの理由と直し方

### 観測ゼロの穴（COLMAP アンカーの間 0.3 s 超）

補間は等速直線・等角速度なので、穴の中で旋回や高度変化があると外れる（#1525〜#1550 は 0.73 s の穴で
158° 旋回 ＋ 4 m 降下、補間は水平直線）。埋め方は `gapmap.ps1`：resolver が外れ値と呼んだ DVR 画像を
`image_deleter` で外し、`mapper --Mapper.fix_existing_frames 1` を上に回して DVR フレーム同士で三角測量させる
（`image_registrator` は既存の 3D 点にしか合わせないので、芝しか写っていないフレームは登録されない）。
3,925 / 3,927 枚が登録される —— **が、そのまま使ってはいけない**：

- 450 行が座標 10⁵ m の発散、192 行が同じフレームの別バッチ（dvr/dvr2/dvr3/dvr4）からの重複
- 芝しか無い区間（#770〜#1039、#4315〜#4428）の新規姿勢は自己整合なだけで数 m ずれていて、隣の正しい
  アンカーまで resolver に外れ値扱いさせる
- **重複を inliers で選ぶと、元の正しいアンカーがゴミに負ける**（102 枚消えて #770〜#994 の向きが
  270 フレームの slerp になり最大 180° 外れた）。**元のアンカーを最優先**、mapper の新規はそのフレームに
  元アンカーが無いときだけ

新規の採否は **DVR 自身で判定する**（`eval_bands.py BLUR=3`）：mapper の姿勢で描いた loss が、直前の
refine 結果の姿勢の loss の 1.05 倍以下なら採る。947 枚中 681 枚が通り、#1511〜#1555 は 40/42、
#770〜#1039 は 1/2。候補の回転は interp60 と同じ `Mz @ R`（`Mz R Mz` ではない。1 回目は全部 100° 外れて
「全部悪化」と出た）。

### ヘアピンで slerp が近道を通る

アンカー間の回転が 100° を超える穴では、slerp の短い弧と実際の経路（長い弧）が違うことがある。
`hairpin_arc.py` で長い弧（四元数の内積を負に強制）を作り、両方を `eval_bands.py BLUR=3` で採点する。
7 か所のうち長い弧が勝ったのは #1662〜#1673 の 1 か所だけ（1.196 → 1.070、10 枚中 9 枚）。

**DVR の隣接フレームから回転を積む「視覚ジャイロ」は、ここでは使えない。** essential 行列も遠景だけの
ホモグラフィも、近い芝の上では 0.3 m/フレームの移動が 1〜3° の回転に化けて 5°/フレーム流れる。
3DGS の深度を足して PnP にすると（`gyro_pnp.py`）普通の穴では閉合誤差 0.8°（0.14°/フレーム）だが、
**肝心のブレた 900 °/s のヘアピンでは 11° しか回らず**、画素比較でアンカーが勝った。効くのは slerp で
足りる場所だけ。LK フレームの向きも使えない（アンカーの向きを引きずり、突然跳ぶ）。

### 離陸前は 1 つの姿勢

#116 まで地上（Saqoosha が DVR で判定）。観測 105 個の中央値（PnP が 1 個 1.8 m 外している。平均は駄目）と
COLMAP フレームの平均回転で 1 姿勢にし、`src: "ground"`。refine は飛ばす。

### 人が打つ対応点（`mark` モード、効いた）

アルゴリズムが動かせるのは数度・1 m まで。それ以上の外れは**人がランドマークを打ち、機械が解く**。
537 印で run 10 の p50 32 px → 7.3 px、30 px 以内 47% → 89%、カメラの後ろに落ちる印ゼロ（`marks_eval.py`：
各印が、その姿勢集合でランドマークを投影した位置から何 px ずれるか。人の真値なので run の採否はこれで決める）。

- **打ち方**：viewer の `mark`（キー `m`）。ランドマーク＝風で動かないもの（フラッグの根元、ゲートの足）、
  `+ new` で追加、数字キーで選択。3D 位置は自由視点で **2 つの視点からクリック**（光線の交点。1 クリックだけなら
  地面 y 1.5 に仮置き。矢印 / PageUp・Down で微調整、`reset 3D`）。DVR の画の上のクリックが、そのフレームの
  そのランドマークの印（黄色の輪。水色の十字は「いまの姿勢だとここに写るはず」）。保存は自動で
  `build/dvr/hdz_0067/marks.json`（dev サーバの `/api/marks`）。**mark モードのタブは 1 つだけ**——後に保存した
  タブが勝つ
- **解き方**：`marks_apply.sh <N> <前の N>`（solve → `interp60` → 長い弧 → 変わったフレーム一覧）、
  その一覧を `refine_batch.py FRAMES=@changedN.txt` で refine、`refined2poses.py` で合流、**印のあるフレームは
  人の解に戻す**（refine が 6 → 10 px に引き戻した）。`marks_solve.py` はフレームごとに再投影誤差で姿勢を解く：
  印 1 個は回転 15° / 移動 8 m に縛り、高度 0.7 m と位置 2.5 m の prior で光線上の点を決める。印 2 個は
  回転 30°（2 点では 6 自由度が決まらず、自由にすると 16 m 滑った）。**印 3 個以上で回転が自由**になり、
  yaw を 5° 刻みで総当たりしてから最小二乗——500 °/s の旋回でランドマークがカメラの後ろに来るフレームは
  これでしか解けない。採用は残差 10 px（3 個以上は 25 px）以内。解いた姿勢は `manual` 観測として
  `interp60.py` に **σ 0.05 m** で入る（0.15 だと印が 10 px 残る。自動観測は 0.3〜1.5）
- 解けないと出たフレームは印を足す：1 個で「カメラの後ろ」→ 同じフレームに 3 個

## 検証は画素で、目視ではない

- `eval_bands.py`（`BLUR=3`）が、2 つの姿勢集合で同じ DVR フレームを描いて帯ごとの loss を出す。
  **run の採否は全部これで決めた**（run 5 と run 6、mapper の候補、長い弧）。1 枚の wipe で見た印象は
  2 回外れた（#184 の鉄塔、#1533 の地平線）
- `eval_offset.py` は「DVR の隣のフレームと比べて loss が区別できるか」と「yaw を振った loss の曲線」を出す。
  loss 関数そのものを疑うときの道具
- **`refined2poses.py` の合流規則**：採用フレームは refine の姿勢、観測のあるフレーム（colmap / lk / ground）は
  不採用なら init のまま、補間フレームは両隣の採用フレームが 0.5 s 以内なら Hermite、遠ければ init のまま
  （1 s 離れた両隣で Hermite すると 4 m 膨らんだ）

## ビューア（`viewer/`）

公開版は **https://ghostline.saqoo.sh/jdl-2026-r6/**（`tools/publish-dvr-viewer.sh jdl-2026-r6 build/dvr/hdz_0067`：

`marks.json` を更新したら同じスクリプトで上げ直す（`rclone --checksum` なので変わったものだけ送る）。
FDF の 6 本は **https://ghostline.saqoo.sh/fdf-2026-r6/**（`tools/publish-dvr-viewer.sh fdf-2026-r6 viewer/public/flights.json`）。
2 つ目の引数が `flights.json` のときは、各飛行の `index.json` が挙げる姿勢集合・動画・既定のシーン・空を `data/<flight>/` に置き
、ページは最初の飛行を開く（`VITE_DEFAULT_DATA`）。一覧のファイルが
手元に無いと止まるので、先に `index.json` をそろえる。

手元は `bun run dev`、`public/data` → `build/dvr/hdz_0067` のシンボリックリンク。SOG は
`npx @playcanvas/splat-transform`（座標は回らない）。web 座標は右手系 x 東・y 上・z 南（Unity の z 反転）。
COLMAP のカメラは x 軸 180° を掛けて PlayCanvas のカメラにする。

- 3 状態：follow off ＝ 自由カメラ ＋ DVR、follow on ＝ DVR 姿勢の 3DGS ＋ DVR、compare ＝ 自由カメラ ＋
  DVR 姿勢の 3DGS に DVR を wipe。compare はキャンバスが行全体で、2 つ目のカメラ `cam2` を `rect` で右半分の
  4:3 の箱に置く（World レイヤーだけ描くので経路の線が写真に乗らない）
- **`addComponent('camera', { enabled: false })` で作ると entity の `enabled` を立てても真っ黒**。entity 側だけで
  切り替える
- **フレーム番号は `floor(currentTime × 60)`**。ブラウザは timestamp ≤ currentTime のフレームを出すので、
  `round()` だと再生中は半分の時間で姿勢が 1 フレーム先を行く（230 °/s で 3.8°）。シークは半フレーム
  ずらして着地させる
- 経路の色は姿勢の出どころ（colmap / lk / interp / refined / ground）、時刻ラベルにも出る。`poses` の
  切り替えで run を比べられる
- 飛行ごとのフォルダ（`public/<flight>` → `build/dvr/<flight>`）の `index.json` が pose 集合の一覧と既定のシーンを持ち、`flights.json` が
  上の `flight` メニュー（`?data=`）
- **`pad` モード**：台の上のフレーム（`ground`）を編集中の姿勢で描く。#0 で compare にして ↑↓←→（カメラの向き基準で地面を移動）、
  W / S（高さ）、Q / E・R / F・Z / X（ヨー・ピッチ・ロール）、shift ×10・option ×1/10。キーは `e.code` で読む（Mac の option ＋ 文字は
  別の文字になる）。3D ビューのクリックで台をそこへ。dev サーバーの `/api/pad` が `<flight>/pad.json` に自動保存
- **シーンの色を変える**：SuperSplat で色を調整したら **Apply を押してから**書き出す（押さないと値は元のまま）。SuperSplat の書き出しは
  Z 軸 180° 回って（x, y の符号が逆）並びも変わるので、`npx -y @playcanvas/splat-transform@3.4.2 -w <in>.ply -r 0,0,180 <out>.sog`
