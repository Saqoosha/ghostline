# 観客とパイロットのためのビューア（ライブとリプレイ）設計

## 目的

レースの会場でスマホから見る観客、家で YouTube の配信と並べて見る人、飛び終わって自分のヒートを見返すパイロットが、
同じページを ghostline のサイト（https://ghostline.saqoo.sh ）で開いて、機体がスキャンの上のどこを飛んでいるかを見る。
会場の rt4090 のライブ追跡（[realtime-tracking.ja.md](../../realtime-tracking.ja.md)）の答えを、LAN の外へ出す。
最初の本番は次の週末の JDL（土曜：練習と予選 1、日曜：予選と決勝のトーナメント）。

いまの会場のページ（操作ページ `http://rt4090:8080`、3D のページ `/view/`）は LAN か Tailscale の中でしか見られず、
操作のための画面で、観客向けではない。

## 目標

1. **ライブのページ**：いま飛んでいるヒートの全員の位置・軌跡・名前・コースの線を、3D で、ほぼ遅れなく
2. **配信に合わせる遅れ**：YouTube の配信は数秒〜30 秒遅れる。ページの表示を見る人が遅らせて、配信とそろえられる
3. **ヒート直後のリプレイ**：ヒートが終わったら、会場の答えだけで、すぐ見返せる
4. **夜の作り直し**：録画から丁寧に解き直した線と、各パイロットの DVR の映像に置き換わる
5. **入口**：大会の 1 日に 1 つ、ヒートの一覧。飛んでいるヒートがあれば先頭に LIVE

5 つとも JDL の土曜に間に合わせる（Saqoosha）。作る順は、ライブ＋遅れ＋入口 → ヒート直後のリプレイ → 夜の DVR 付きリプレイ。
最後のものは、土曜の夜に回して日曜の朝に土曜のヒートが見られれば間に合ったとする。

## 目標にしないこと（いまは）

- ライブのページでの映像（DVR もレースの中継も）。映像は配信で見てもらう
- 自分の線と他の人の線を比べる機能（別のヒートの線を重ねるなど）。後で考える
- 順位・ラップの計算（ゲートの位置がまだ無い）
- スマホ向けの画面（最初はパソコン。崩れなければいい）

## やってはいけないこと（動いても失敗）

- **会場の電池と回線を見る人の数に比例して食う形。** rt4090 は電池（DELTA 2 Max、1 日で 84〜91%）で、回線はテザリングのこともある。
  見る人が 1 人でも 1,000 人でも、会場が出すのは 1 本の流れだけ
- **配信より先にネタバレする形。** 遅れを付けた人には、名前・ヒートの切り替え・LIVE／LOST も同じだけ遅らせて出す
- **会場の追跡を止めたり遅くしたりする形。** 送るのは答えの数字だけ。送れなくても tracker は止まらない
- **他人を装う、運営の公式に見える形。** 「位置は DVR の映像から推定したもの」と、ページに書く

## 決まっていること（Saqoosha）

- ライブは位置と軌跡だけで、映像は無し
- リプレイは「ヒート直後は会場の答えだけで速く」「夜に作り直して DVR 付きに」の 2 段。会場の PC は電池なので、重い処理は夜
- リプレイは単純な見返しでいい（比べる機能は無し）
- **見た目は操作ページ（`tools/dvr/rt_control.html`）と同じ作法**：紙の色の地、細い線、細い文字、ghost —— line のロゴ、マスごとの色
  （`--tl` `--tr` `--bl` `--br`）、端末に入っている字体だけ
- **ライブのページは MGP のページ（`viewer/mgp.html`／`src/mgp.ts`）を簡単にした形**：DVR のタイル・タイムライン・順位は無し
- 最初はパソコンの画面

ライブのページの下書き（Saqoosha が「great」と言ったもの）：3D がページ全体。上の帯にロゴ・大会とヒートとクラス（例「FDF 2026-10-17 · HEAT 7 · EXPERT」）・
LIVE の赤い点・カメラの切り替え（ORBIT・TOP・FOLLOW）。左上に出場者の欄（色・チャンネル・国旗・名前・状態 FLYING／LOST／NO PICTURE、押すとその人を追う）。
3D の中に名前のタグ。下の帯に断り書きと前のヒートへのリンク。

## ぼくが決めたこと（違えば Saqoosha が直す）

### 流れ

```
rt4090（会場）                         Cloudflare                                    見る人
rt_track.py ─PUSH(SSE)→ rt_control.py ─1 本の WebSocket→ Durable Object（中継）─→ ライブのページ（WebSocket）
              └ ヒートが終わったら、そのヒートの答え ─→ Worker の書き込み口 ─→ R2 ─→ リプレイのページ
夜：録画から解き直し（rt_replay_day.sh 系）＋ DVR の切り出し ─→ R2（同じヒートを置き換え）
```

- **中継は Durable Object（大会の 1 日に 1 つ）**。rt4090 からの 1 本を受けて、見る人全員に配る。見る人の数が会場に影響しない。
  中継は直近 60 秒の答えを持っていて、つないだ人にまず渡す（遅れを付けた人がすぐ描けるように）
- **会場側の送り手は `rt_control.py` に置く**（tracker 本体ではなく）。tracker の PUSH を受けて、ヒート管理の名前とヒート番号（`/api/pilots`）を添えて送る。
  送れない間は捨てる（ためない）。tracker の速さに影響しない
- **ヒートの区切り**：ヒート管理のヒート番号かクラスが変わった時刻と、全マスの絵が 30 秒以上消えた時刻の、早いほう。ヒート管理がいつ番号を進めるか（呼び出し時・開始時・終了後）は
  わからないので、絵の有無の区切りを主にして、番号とクラスと名前は「そのヒートの絵が出ていた間にヒート管理が返していた値」を付ける。ヒート管理に届かない日は名前が空で、番号の代わりに時刻で呼ぶ。
  FDF（2026-10-17）では途中で会場の LAN が変わってヒート管理に届かなくなった
- **ヒートの名前（置き場所の鍵）は開始時刻＋番号**（例 `heats/101530-h7/`）。練習と予選で番号が繰り返されても、飛び直しでも上書きしない
- **送り手はヒートごとの開始と終わりの時刻（壁の時計）を rt4090 にも書く**（`~/rt/live/heats-<日付>.jsonl`）。録画の `.json` は開始の壁の時刻（`start`）を持っているので、夜の作り直しはこれで録画のどこがどのヒートかを決める
- **ヒート直後のリプレイ**：区切った時点で、そのヒートの答え（`.jsonl` の行、マスごと）と名前を 1 つの JSON にまとめて、Worker の書き込み口へ送る（gzip で数百 KB）
- **書き込み口の守り**：Worker の書き込み（中継への送り、R2 への置き場）は、rt4090 だけが持つ鍵で守る。鍵の正本は 1Password。rt4090 には 1Password のアプリが無いので、Mac から 1 度だけ `~/.config/ghostline/key`（600）に置く（値は画面にもログにも出さない。Worker 側は secret）
- **夜の作り直し**：録画を tracker にもう一度流して（`tools/dvr/rt_replay_day.sh`、いまはライブと同じ精度）、
  さらにオフラインの丁寧な解き方（`cpr_*` 系）が使えるならそれで。DVR の映像は、録画の 2×2 からマスごとに切り出して 1 人 1 本の mp4（MGP と同じ形）
- **データの置き場所**：R2 の `dvr/<大会>-<日付>/` の下（大会の 1 日が単位。JDL の土曜と日曜は別）。今の公開の仕組み（`tools/publish-dvr-viewer.sh`）と同じ。ヒートごとに `heats/<開始時刻>-h<番号>/race.json` と映像。
  中継の Durable Object も同じ名前で 1 日に 1 つ
- **シーンとコースの線**：シーンは前の晩に作って `.sog` にし（Mac で。rt4090 に node は無い）、その日の置き場所に上げておく。RTK で撮れば 2 日のシーンは同じ座標なので、コースの線は日をまたいで使える。
  コースの線は最初の数ヒートの答えから `rt_trackline.py` で作って上げる（数十 KB、テザリングでも足りる）。ページは「線がまだ無い」と「途中で差し替わる」を扱う
- **試験用の置き場所**：同じ Worker に `staging-` で始まる大会名を許して、R2 の場所と Durable Object を分ける。公開の入口の一覧には出さない

### 画面

- **ライブ**：今日の 3D のページ（`viewer/src/livepage.ts`）の描き方（全員・MGP 風の線とタグ・コースの線・Orbit／Top／Free／Follow）を、
  見た目だけ操作ページの作法にした新しいページ。入力は SSE ではなく中継の WebSocket
- **遅れ**：上の帯に DELAY。0 秒から 60 秒、0.5 秒刻みの －／＋、目安のボタン（低遅延 約 7 秒、通常 約 20 秒）。ブラウザに覚えさせる。
  答え・名前・ヒートの切り替え・状態を全部同じだけ遅らせる。**入口の一覧と「前のヒート」のリンクも、その人の遅れの分だけヒートの終わりを遅らせて見せる**（終わったヒートが配信より先にリプレイとして現れない）
- **リプレイ**：MGP のページの作りを土台に、タイムライン（再生・一時停止・ドラッグ・速さ）、カメラ（ライブと同じ）、
  夜の版では右に DVR のタイル。ヒート直後の版か夜の版かを小さく出す
- **入口**：大会の 1 日の一覧（番号・クラス・出場者・時刻）。飛んでいるヒートがあれば先頭に LIVE
- **国旗**：今日の推定（漢字・かな → JP、韓国の姓 → KR）と、大会ごとの `countries.json` での上書き

### 土台にするもの

- 3D の描き方：`viewer/src/livepage.ts`、`live.ts`（main にある）
- リプレイ：`viewer/mgp.html`、`src/mgp.ts`、`src/racekit.ts`。**main にまだ無い**（ブランチ `reconstruct-mgp-qualifier-tracks` にある）。
  そのブランチが main に入るのを待つか、使う部分だけ写す
- 見た目：`tools/dvr/rt_control.html` の CSS（`:root` の色と字体、`.mark`）
- Worker：`worker/src/index.ts`（R2 を読むだけの今の作りに、書き込み口と Durable Object を足す。設定は `worker/wrangler.jsonc`）

## 作る人に任せること

- ページとデータの細かい形（race.json に何を足すか、ライブの WebSocket の 1 行の形）
- 中継が持つ 60 秒の持ち方、つなぎ直しの作法
- 入口のページの見た目（操作ページの作法の範囲で）
- 夜の作り直しを手で回すか、台本 1 本にするか

## 確かめ方

- 今日（2026-10-17）の録画を `rt_replay_day.sh` で流し、`rt_control.py` の送り手を通して、ステージングの中継とページに出す。会場の代わりになる
- 遅れ：同じ録画を YouTube の非公開の配信に流して、ページの DELAY でそろえられるかを見る
- 電力：送り手を足した前後で、rt4090 の GPU＋CPU の平均（`rt_power_linux.sh`）が変わらないこと
