# 飛行中の現在位置をリアルタイムに出す

レース中に、各パイロットのライブ映像（HDZero、60 fps）だけから機体の位置を 3DGS のスキャン上に出す。オフラインの通し
（[dvr-localization.ja.md](dvr-localization.ja.md)）は 1 フレーム約 1 秒で、束調整が未来のフレームも使うので、ライブには
そのまま使えない。ここは別の設計で、**過去のフレームだけで 1 フレーム十数 ms** に収める。調査の全体は
[research/2026-09-29-realtime-flight-position.md](../research/2026-09-29-realtime-flight-position.md)。

会場の 2×2 を SRT でオフィスへ送る経路は、試験の送り手（`rt_send.py`）から通してある。USB キャプチャから答えをページに描くところまでは、
屋内の Whoop で通した（下の「屋内の Whoop」）。残るのは本物の NDI の入力。

## しくみ

| 段 | 道具 | 中身 |
|---|---|---|
| 地図（事前、1 回） | `tools/dvr/rt_map.py` | 他の飛行の `poses60_pad.json` と scan cameras の姿勢で 3DGS を 640×480 に描き、XFeat 2048 点を描画の深度で 3D に上げる。DINOv2 の全体記述子も。1 m・20° 以内に既にあるものは間引く |
| 追跡（毎フレーム） | `tools/dvr/rt_track.py` | 前の答えから等速で予測 → 近いキーフレーム 2 枚と LighterGlue → PnP（PoseLib）。答えが 0.33 s 無ければ DINOv2 で探し直す |
| 描く点 | ページ（`viewer/src/live.ts`） | **100 ms 遅らせ、そのフレームの前後に届いた答えに 2 次式を当てて描く**（外挿しない）。後ろの答えがまだ無ければ最新の答えで止め、0.3 s 超は「見失い」。tracker は生の答えを送るだけで、描き方はページが決める |
| 軌跡 | 同上 | 答えが届くたびに直近 0.5 s を描き直す（前後 0.25 s の答えに 2 次式）。外れた点も次の答えで直る |

**レースは 1 プロセスで全員を回す。** 毎周、各パイロットの一番新しいフレームを取り、XFeat を全員分 1 回、照合を全組
（見失った人の再局在化の候補も含む）1 回のバッチで、PnP は人数分のスレッドで。さらに次の周の XFeat と照合を、この周の
PnP の間に走らせる（`PIPE=2`、次の周の予測は 1 周古い答えから作る）。

**地図に試す飛行自身を入れない。** 「他の飛行から作った地図に、初めての飛行として照合する」が本番と同じ条件。
レースの機体はほぼ同じ線を飛ぶので、他の飛行の経路に沿って描いた視点が効く。

## 使い方（win4090 の WSL、mastenv）

作業場所は `C:\Users\saqoosha\VDGS\dvr\rt`。XFeat は `~/xfeat`（git clone、重みは同梱）、kornia・`poselib`・`tensorrt-cu12`（11.3）・`onnx`・`onnxscript` は mastenv に入れた。

~/mastenv/bin/python rt_trt.py bench-xfeat ../fdf-r6b-d05/dvr_pinhole.mp4 eng/xfeat_fp32.engine

Git Bash（win4090 のログインシェル）から `wsl ... bash -l /mnt/c/...` を打つと、パスが `C:/Program Files/Git/mnt/c/...` に書き換わる。`MSYS_NO_PATHCONV=1 wsl ...` で止める。

出力は `<出力>.json`（ライブの点、viewer の姿勢集合の形）と `<出力>_trail.json`（軌跡）と `<出力>.jsonl`（答えの記録）。
viewer では `poses60_rt.json` / `poses60_rt_trail.json` として飛行のフォルダに置き、`index.json` に載せる。色は

ssh 越しに `$p` のような変数を使うループは引用で消える。スクリプトにして `bash <file>` で呼ぶ。

**描き方は Saqoosha が live 表示で見比べて決めた**：外挿は見た目が悪く、100 ms 遅らせた内挿は遅れを感じない。電波の乱れで止まるのは許容。
数字でも、描く点の p90 を押し上げていたのはほぼ全部が外挿だった（d05 1 本：外挿 1.38 m → 33 ms 遅れで 0.91 m、67 ms で 0.76 m。挟めた点だけなら
答えそのものと同じ p90 0.7 m 前後。4 本同時の d05 は 100 ms で 86% のフレームを挟めて p90 0.74 m）。`rt_track.py` の `.json`（カルマンで外挿した点）と
`_trail.json` は再生での採点用に残してある。ビューアの `live` は `index.json` の `live` に挙げた答えの記録（`rt_track.py` の `.jsonl` から `how` が none 以外）を、
答えの出た時刻どおりに流して描く

## 基準値（RTX 4090、TensorRT＋PoseLib、2026-10-05）

この節の「描く点」は `rt_track.py` の外挿した点（`.json`）。ページの 100 ms 遅らせた内挿は上の段落の数字。遅延はフレームが届いてから姿勢が出るまで。

| | PyTorch＋MAGSAC（`GLUE` / `XFEAT` なし、`PNP=magsac`） | TensorRT＋PoseLib（`RENDER=0`。遅延を取るとき） |
|---|---|---|
| d05 1 本：処理 / 1 周 p50 / 遅延 p50 | 56 Hz / 15.6 ms / 36 ms | **60 Hz（全フレーム）/ 6.7 ms / 11 ms** |
| d05 1 本：答えの位置 p50 / p90・向き p50 | 0.24 / 0.77 m・0.5° | 0.19 / 0.72 m・0.4° |
| d05 1 本：描く点 p50 / p90・向き p90 | 0.54 / 1.38 m・9.3° | 0.50 / 1.24 m・3.1° |
| 4 本同時：1 周 p50 / 遅延 p50 | 28 ms / 52〜63 ms | **8.7 ms / 18〜23 ms** |
| 4 本同時：処理 | レース 25 Hz・d05 33 Hz | 全員が全フレーム（レース 30 Hz・d05 59 Hz） |
| 4 本同時：描く点 p90（KNT / SENA / SAQ / d05） | 9.9 / 4.0 / 2.0 / 1.77 m | 3.4 / 2.4 / 2.3 / 1.18 m |

精度を取るなら、これに予測姿勢での描画（`RENDER=1 RCLIP=2`、下の節）を足すのが推奨：d05 1 本は答え 0.11 / 0.47 m・遅延 15 ms、4 本同時は遅延が約 35 ms に伸びる。
4 本同時はレース 3 本（中継の 4 分割から切った 30 fps・半分の解像度）＋ d05。4 本同時の描く点の p90 は同じ設定でも回ごとに 1〜2 m ぶれるので、確かなのは Hz と遅延。
軌跡（200 ms 遅れ）は d05 1 本で p50 0.27 m / p90 0.65 m（揺れ 1.8 cm、束調整の経路と同程度）。本番のライブは 60 fps・フル解像度なので、d05 に近いはず（未確認）。

**MacBook Pro（M1 Max、GPU 32 コア）**：`DEV=mps XFEAT_DIR=<clone>` で動く（`poselib` が要る。`GLUE` / `XFEAT` は CUDA 専用。PoseLib は Mac では未計測）（XFeat と LighterGlue は CUDA が無いと CPU に置かれるので MPS へ移す。
MPS の `interpolate(mode="area")` は割り切れない大きさで落ちるので、再局在化の縮小は bilinear＋antialias）。d05 1 人で、2048 点・キーフレーム 2 枚
は 10 Hz（照合 64 ms）、**1024 点・1 枚（`TOPK=1024 MAPK=1024 NKF=1`）で 17 Hz**、答えの位置は変わらず p50 0.35 m。けど 17 Hz でも約 70 回見失い
（4090 では 5〜8 回）、描く点は p50 2 m。512 点は対応が足りず見失いが増えて逆に遅い。MPS では照合のバッチがほとんど効かず（1 組約 22 ms、4090 は 2.2 ms）、
4 人は 1 人 5 Hz 前後の見込みで無理。会場で処理するなら NVIDIA の GPU のノートが要る（送る分の約 220 ms も消える）。

**1 人 10 Hz では足りない見込み。** 60 fps で 6 フレームおきだと、800 °/s の旋回で答えの間に 80° 回り、予測から近いキーフレームを
選ぶ仕組みが外れる。4 プロセスを並べた版（1 人 12〜20 Hz）では描く点の p90 が 10 m 以上に崩れた。

## 予測姿勢でその場で描いて照合する（`RENDER=1`）

追跡中は地図のキーフレームを使わず、各ストリームの予測姿勢でその場で 3DGS を描き（`tools/dvr/rt_render.py`）、XFeat を掛けて描画の深度で 3D に上げ、
フレームをその 1 枚だけに照合する。キーフレームは見失ったときの探し直しと、追跡に失敗した直後の 1 回（`RFALL=1`）だけに使う。

```bash
GLUE=eng/glue_mix.engine XFEAT=eng/xfeat_fp32.engine RENDER=1 RCLIP=2 SCENE=/mnt/c/Users/saqoosha/VDGS/scenes/FDF-2026-R6b-spirula-web-dvr2.ply \
  ~/mastenv/bin/python rt_track.py map_fdf-r6b-d05.npz,../fdf-r6b-d05/dvr_pinhole.mp4,out_d05,truth-d05.json
# オフィス：SCENE=/mnt/d/office-floor-video/office-7f-yup.ply RNEAR=0.1（地図を作ったときの near に合わせる）
```

| d05 1 本（TensorRT＋PoseLib） | 答え p50 / p90 | 描く点 p50 / p90 | 処理 / 遅延 p50 / p90 |
|---|---|---|---|
| キーフレーム 2 枚（`RENDER=0`） | 0.19 / 0.72 m | 0.50 / 1.24 m | 60 Hz / 10.8 / 13 ms |
| **`RENDER=1 RCLIP=2`** | **0.11 / 0.50 m** | 0.43 / 0.96 m | 60 Hz / 14.6 / 16 ms |
| 新しいコース（合成の視点 4 m 格子の地図）、`RENDER=0` → `1` | 0.36 / 1.19 → 0.11 / 0.46 m | 0.70 / 2.61 → 0.41 / 1.15 m | |

- **キーフレームと視点がずれていたことが誤差の多くだった。** オフラインで、同じ 991 フレームを次の 4 通りで比べた（`rt/trt/exp_render.py`）。
  - キーフレーム 2 枚：0.19 m
  - 予測姿勢で描いた 1 枚：0.12 m
  - 答えで描き直す 2 周目まで：0.11 m
  - 参照の姿勢で描いた 1 枚：0.08 m
  
  描いた 1 枚にキーフレームの対応を足すと、かえって悪くなった（0.14 m）。ライブでは、良い答えから予測するのでオフラインより良い
- **新しいコースの地図は、スキャンのカメラだけで足りる。** 地図の視点は探し直しにしか使わないので、4 m 格子の合成でも、スキャンのカメラ 543 枚だけの地図（`nc/map_scan.npz`）でも、
  答えは 0.11 / 0.46〜0.49 m で他の飛行の地図と同じになる（スキャンだけの地図は `RENDER=0` では 0.70 / 2.85 m で使えなかった）。合成の視点（地図作り 7 分）は要らない
- **オフィスのクリップ**：答え 0.09 / 0.30 → 0.07 / 0.23 m、描く点 p90 0.50 → 0.35 m。参照の姿勢で描くと 0.04 m まで下がる。つまり残っていた約 7 cm のずれは地図のずれではなく、照合の対応の質から来ている
- **描画が時間のほとんど**。スキャンは 202 万 splat で、1 視点に約 119 万入り、描画 8.4 ms・XFeat 2 ms かかる。
  - `RCLIP=2`（gsplat の `radius_clip`、2 px 以下の splat を飛ばす）で描画は 2.4 ms になり、精度は同じ。`RCLIP=3` は p90 0.56 m で、少し悪い。
  - 不透明度で splat を間引く `ROPA` は精度が落ちる。0.3 で 0.18 / 0.80 m、0.5 で 0.30 / 1.07 m。
  - 320×240 で描くと、かえって遅い（12.7 ms）
- **4 本同時**（`RCLIP=2 RFALL=1`、`PIPE` は `RENDER` のとき既定で 1）：1 周 8.8 → 16 ms。レースの 3 本は全フレームを処理し、遅延 p50 は 19〜23 → 33〜38 ms に伸びる。
  答えも描く点も全員良くなった。

  | 4 本同時 | `RENDER=0` | `RENDER=1`（`PIPE=1`） |
  |---|---|---|
  | 答え p50：KNT / SENA / SAQ / d05 | 0.41 / 0.24 / 0.26 / 0.19 m | 0.32 / 0.13 / 0.21 / 0.11 m |
  | 描く点 p90：KNT / SENA / SAQ / d05 | 3.4 / 2.6 / 2.3 / 1.22 m | 3.1 / 1.5 / 1.7 / 0.97 m |

  - **`PIPE=2` のままだと KNT の描く点 p90 は 5.2 m で、`RENDER=0` より悪い。** `PIPE=2` は次の周の照合を先に回すので、予測が 1 周古い答えから作られ、外れた予測で描くことになる。1 本だけなら `PIPE` の 1 と 2 で差は無い
  - **追跡に失敗した直後の 1 回はキーフレームも足す（`RFALL=1`）。** 外れた予測で描いた画はフレームとあまり重ならない。キーフレームは外れに対する許容幅が広い（45°・12 m）。切ると KNT の見失いが 32 回に増える
- **前の描画は使い回せない。** オフラインで、描画を 1〜3 フレーム古いものにして測った。
  - d05（60 fps）：0.116 → 0.147 / 0.188 / 0.248 m
  - レースの KNT（30 fps）：0.34 → 0.51 m、解けた割合 97 → 92%
- **描画をカメラごとに描かず、4 台分まとめて 1 回で描く（`RBATCH=1`）。** 4 台分の描画が 10 → 5 ms、遅延が約 4 ms 縮む。けど、精度が少し落ちる（SENA 答え p90 0.75 → 0.85 m）ので、既定は切ってある。
  - 精度が落ちる理由：視野外の splat を切る範囲が 4 台の和になる（`frustum.py` の理由）
  - 別々の CUDA ストリームで並べる手は 10.2 → 8.6 ms にしかならない
- **対応点のサブピクセル精緻化（XRefine、`boschresearch/xrefine`、AGPL-3.0）は効かない**：描いた側の点を固定してフレーム側を動かす general 版で、d05 0.111 / 0.48 → 0.112 / 0.50 m、
  オフィス 0.069 → 0.072 m（向きだけ d05 0.35 → 0.30°）。small 2.4 ms・large 4.3 ms かかる。参照の姿勢で描いた 1 枚（0.08 m）との差は、点の位置の細かさでは埋まらない
  （その差のどれだけが参照の経路そのものに寄った分かは、独立した真値が無いので分けられない）
- **描画の深度の縁にある点を捨てる（`REDGE`）は差が出ない**：5×5 の深度の幅が深度の 0.1 倍を超える点を捨てると d05 0.11 → 0.10 m・オフィス 0.07 → 0.08 m で、
  ぶれの範囲。0.05 以下は浅い角度の地面の点まで消えて悪くなる（0.02 で解けるフレームが半分）。既定は切ってある
- 4 本同時の 1 周 16 ms の内訳：描画と XFeat 7.5、照合 5.7、特徴 3.7 ms、残りは予測と探し直し

## ライブ入力：会場の 2×2 → SRT → オフィスの 4090

4090（win4090）はオフィスにあり、会場には持って行けない。会場では Event VRX の映像が NDI の 2×2（中継と同じ、1 マスが
4:3 の魚眼を 16:9 に引き伸ばしたもの）で取れる。形は：

会場：OBS（NDI プラグイン）で NDI を受け、1 本の映像として SRT で送る → オフィス：`rt_track.py` が SRT を受けて各マスを
640×480 のピンホールに直接写し（4:3 に戻す・魚眼補正・縮小を 1 回の remap で）、全員を本物の時計で追跡する。会場側はコードを書かない。

```bash
# オフィス（win4090 の WSL、rt/）：3 マス。ほかのマスも同じ形で足す
U="srt://0.0.0.0:9000?mode=listener&latency=80000"; CAM=../race-sf-sena/dvr_pinhole.mp4.json
GRID=1280x720 GRID_FPS=30 ~/mastenv/bin/python rt_track.py \
  "map.npz,$U|0:0:640:360|$CAM,live/sena" "map.npz,$U|640:0:640:360|$CAM,live/saq" "map.npz,$U|640:360:640:360|$CAM,live/knt"
# 試験の送り手（Mac、会場の代わり）：準決勝の 4 分割を実時間で。T0 に受け手の SEND_T0 と FRAME_CODE=40:400 を合わせると遅延が正確に出る
uv run --with numpy python tools/dvr/rt_send.py <T0> ~/Downloads/fdfcupr6-amain-semifinal.MOV "srt://100.68.63.104:9000?latency=80"
```

WSL の Tailscale の住所は `100.68.63.104`（wsl4090）。WSL の ffmpeg は SRT を話すが、Mac の Homebrew の ffmpeg は話さないので、
送り手は `srt-live-transmit`（`brew install srt`）で UDP から中継する。4 分割のマスは素直な四等分（左上 SENA、右上 SAQOOSHA、右下 KNT、
左下は空き）。前に作ったレースのピンホール映像と相関 0.9994 で一致した。

**Mac からオフィスまで通した結果**（準決勝の 3 人、720p の 2×2 を 8 Mbps、SRT の待ち 80 ms、x265 ultrafast zerolatency）：2,250 フレーム全部届き、
3 人とも 25 Hz、答えの位置 p50 0.36・0.36・0.56 m（ファイルから読んだときは 0.29〜0.46 m）。**送ってから姿勢が出るまで p50 278 ms**
（エンコードとデコード約 120 ms、SRT 80 ms、回線約 20 ms、tracker 約 58 ms）。

**GStreamer で RTP を SRT に載せると 78 ms 短い**（`rt_send.py GST=1 SIZE=854x480` → `rt_track.py GRID_GST=1`）：Mac → オフィスで送ってから届くまで
p50 142 ms（ffmpeg＋mpegts は 220）、送ってから答えまで 200 ms（278）、精度は同じ。Mac の中だけで測ると、送ってからデコードまで ffmpeg＋mpegts over SRT 約 200 ms、
GStreamer＋mpegts over SRT 164 ms、**GStreamer＋RTP over SRT 125 ms**、RTP over 素の UDP 47 ms（再送が無いのでインターネットには向かない）。mpegts そのものが約 35 ms、
ffmpeg の受信側が約 30 ms 溜めていた。SRT はパケットの区切りを保つので、RTP を `mtu=1316` で割ればそのまま載る。WSL には GStreamer を root で apt で入れた
（`wsl -d Ubuntu-24.04 -u root`。saqoosha の sudo はパスワードが要る）。会場の送り手は OBS の代わりに GStreamer の 1 行で書ける見込み
（`ndisrc ! ndisrcdemux ! videoconvert ! videoscale ! x264enc tune=zerolatency ! rtph264pay mtu=1316 ! srtsink`。`ndisrc` は Mac の Homebrew 版にある。本物の NDI では未確認）。
**解像度は遅延にも効かない**（x264 で 1280×720〜640×360 が 115〜117 ms）。

遅延で効いたこと（Mac の中だけで組んで部品ごとに測った。送ってからデコードまで）：
- **受信側 ffmpeg の先読みを絞る**（`-probesize 500000 -analyzeduration 200000`）。既定だと最初の約 5 秒のフレームが消えた
- **Mac のハードウェアエンコーダは遅い**：VideoToolbox は H.264 も HEVC も約 285 ms、x264 / x265 の `-tune zerolatency` は 121 / 137 ms。
  会場の PC も OBS のソフトウェアエンコード（x264 か x265、zerolatency）にする
- **SRT の待ちは設定どおりに足される**（120 → 20 ms で 100 ms 減った）。回線の往復は約 40 ms。切れやすい回線なら待ちを伸ばす
- 効かなかった：デコーダのスレッド（1 本・スライス並列）、送り手のフレームレート調整。コーデック込みの下限約 120 ms の中身は未解明

**解像度は効かず、ビットレートだけが効く**（d05、30 fps、HEVC NVENC、表示は 100 ms 遅らせた内挿で採点）。同じビットレートなら 320×240・480×360・640×480 が
ほぼ同じ：1 人 2 Mbps で表示の p50 0.31 m・p90 1.04〜1.18 m、1 Mbps で 0.35 m・1.36〜1.42 m。640×480 の 4 Mbps で p90 0.85 m。4 人なら 8 Mbps が目安
（回線が細ければ 4 Mbps）。縮めても帯域は減らず、会場のエンコードが軽くなるだけ。理由は未確認（画が動きブレと圧縮でもともとぼけている、XFeat は
8 分の 1 の格子で特徴を探す、の推測）。tracker 自体を小さい画で回せば速くなるかは未試行。

1080p の 2×2 なら 1 マスは 4:3 に戻して 720×540 で、tracker の 640×480 より大きい。OBS の出力を 1704×960 に縮めれば 1 マスがちょうど
640×480 になり、tracker には何も失わない（画素は 79%）。未計測。

## 会場から 4090 へ送るときのビットレート

d05 を NVENC の低遅延設定（`-preset p4 -tune ll -rc cbr -bf 0`、VBV 0.5 s）、640×480 の 1 人分で作り直して測った：

| | 描く点 p50 / p90 | 1 m 以内 | 軌跡 p50 / p90 |
|---|---|---|---|
| 元の映像（60 fps、14.7 Mbps、960×720） | 0.54 / 1.36 m | 81% | 0.27 / 0.68 m |
| **HEVC 30 fps 4 Mbps** | 0.52 / 1.33 m | 82% | 0.27 / 0.70 m |
| HEVC 30 fps 2 Mbps | 0.55 / 1.63 m | 77% | 0.30 / 0.77 m |
| HEVC 30 fps 1 Mbps | 0.59 / 2.14 m | 73% | 0.33 / 0.85 m |
| HEVC 60 fps 8 Mbps | 0.56 / 1.39 m | 79% | 0.29 / 0.71 m |
| HEVC 60 fps 4 Mbps | 0.57 / 1.54 m | 78% | 0.29 / 0.74 m |
| H.264 60 fps 4 Mbps | 0.60 / 1.75 m | 74% | 0.31 / 0.84 m |

**30 fps・HEVC・4 Mbps で品質を保てる（4 人で 16 Mbps）。** 60 fps は 8 Mbps でも届かない。30 fps で落ちるのは描く向きだけ
（2.3° → 3.3°、答えが半分になるため）。TensorRT＋PoseLib の tracker は 4 人でも 60 fps を全部処理できるが、送る帯域では 30 fps が得。
H.264 は同じ精度に約 2 倍のビットレートが要り、1 Mbps 以下で崩れる（0.5 Mbps で描く点の p90 が 7〜16 m）。
確かでないこと：d05 の 1 本だけ、会場の PC のエンコーダ（VideoToolbox / QSV）は NVENC より多く要るかもしれない、元が既に再エンコード、回線は未計測。
作り直しと採点は win4090 の `rt/bitrate*.sh` と `rt/score.py`（出力は `rt/br/`）。

**白黒で送っても tracker は困らない**（XFeat は入力で 3 色を平均し、LK も灰色で見る）。同じ画質（HEVC constqp）なら白黒は 13〜14% 小さい。
同じビットレートでは 2 Mbps で差なし（表示の p90 1.08 / 1.14 m）、1 Mbps 1.38 → 1.23 m、0.5 Mbps 3.29 → 2.73 m と低いほど少し効く。

## 屋内の Whoop を USB キャプチャから（オフィス 7F）

アナログの Tiny Whoop の受信機の HDMI を USB キャプチャ（Guermok）で Mac に取り込み、オフィスの 3DGS（THETA V の動画から作ったもの、
VDGS `docs/spirula.ja.md`）の上に位置をライブで出す。スキャン・クリップ・録画は worktree をまたいで `build/dvr/office-whoop-1/` にある
（`viewer/public/office-whoop-1` はそこへのリンク）。

```bash
# win4090（WSL、rt/）：待ち受け。office/live.env が MAP / GRID / GRID_CROP / CELL と GLUE / XFEAT / RENDER=1 / RCLIP / SCENE / RNEAR=0.1 を持ち、
# 送り手が切れると読み直して立ち上がり直す。旧版（PyTorch＋MAGSAC）は rt_track.py.bak-20261005 と office/live.env.bak-20261005
bash run_live2.sh                       # スケジュールタスク whoop-live。止めるのは office/live.stop を置いて python を kill（起こすときは live.stop を消してタスクを起動）
#   中身: (live.env) GRID_FPS=60 GRID_GST=1 PUSH=8765 rt_track.py \
#         "office/map_office2.npz,srt://0.0.0.0:9000?mode=listener&latency=80000|0:0:640:480|../office-whoop-1/dvr_pinhole.mp4.json,office/live/runN"
# Mac：取り込み → 送信、送った映像と答えの記録。止めるのは <rec>/stop を置いて gst を kill -INT
bash tools/dvr/rt_capture.sh build/dvr/office-whoop-1/rec
bash tools/dvr/rt_replay.sh build/dvr/office-whoop-1/rec [名前]      # 録ったものを再生用の mp4 + json に
# ページ（viewer の dev サーバー）
#   live.html?data=office-whoop-1                                   ライブ。右上はブラウザがキャプチャを直接読んだ画
#   live.html?data=office-whoop-1&replay=<名前>&from=30&to=175      録画の再生（スライダーを飛行なしで試す）
```

- **答えはその場で流れる**：`rt_track.py` の `PUSH=<ポート>` が Server-Sent Events で 1 行ずつ出す（`.jsonl` の行＋`stream`・`fps`）。
  ページ（`viewer/src/livepage.ts`）は `live.ts` の描き方（遅らせた内挿、軌跡の当て直し）をそのまま使い、`trail`・`smooth`（当てはめの窓、
  端に向けて重みを下げる）・`delay` をスライダーで変える。視点とスライダーはブラウザに残る
- **ページの時計は tracker の時刻（`done − lat`）で数える。** フレーム番号 ÷ 60 だと、キャプチャが 59.2 fps のとき 1 秒に 13 ms ずつ先走り、
  追跡できているのに LOST になる
- **地図は前の飛行の答えから育てられる**：キーフレームは 3DGS を描いた画なので、視点は飛んだあたりにあれば足りる。ライブの答え
  （inlier 150 以上）を `{"poses": [{pos, quat, src: "ba"}]}` にして `rt_map.py` に渡す（`STEP=0.4 ROT=20 NEAR=0.1`、17 秒）。
  最初の地図はオフラインで解いたクリップの経路＋参照カメラ（THETA の撮影位置に、水平 8 方位を立てたもの）

**送り手の出口は `sync=false`。** 既定（時計に合わせて待ってから送る）だと、Mac ではフレームが 40〜60 ms たまってから 5 ms 間隔でまとめて出る
（到着間隔 p50 8 ms・p90 51 ms、30 ms 超が 22%。`sync=false` で 16 / 22 ms・4%）。tracker は最新の 1 枚だけ処理するので、処理の回数が塊の数になる
（22.5 Hz。等間隔なら 51.2 Hz、1 周 p50 18.8 ms）。**回線・SRT・デコーダのスレッド・パイプの量は原因ではなかった**（素の UDP、Mac のループバック、
`max-threads=1`、16×12 の画でも同じ形）。録画の PTS は等間隔（16〜17 ms）なので、カメラは無実。切り分けは受信パイプラインだけを動かして到着間隔を測る
（win4090 の `rt/probe_rx.py`）。`rt_send.py GST=1` の試験送り手は `identity sync=true` で時刻を刻むので、Mac から流すと同じ塊が出る。試験は WSL の中から流す
（`rt/wslsend.sh`）。

**受信の画は小さくてよい**（`GRID_CROP` で中央を切って縮めてからパイプへ）：1280×720 のまま 22.5 Hz、640×480 で 29.5、320×240 で 31.5（どれも塊で届く条件）。
精度は変わらない（解けた割合 97%、inlier 中央値 288〜297）。前に測った「解像度は効かない」と同じ。

**基準値（RTX 4090、アナログ Whoop、1 人）**
- クリップ（25 fps、束調整の経路が真値、自分を含まない地図）：答えの位置 p50 0.09 m・p90 0.30 m、向き 1.2°、解けたのは飛行中の 93%
- ライブの飛行（60 fps）：処理 32 Hz（塊で届いていたとき）、解けた割合 92〜93%、inlier p10 / p50 / p90 79 / 236 / 432、0.3 秒超の見失いは 145 秒に 3 回・1.8 秒
- 録画（`office/f2/sent.mp4`）を WSL の中から SRT で流したとき（`wslsend.sh`、受け方は `run_live2.sh` と同じ）：届いてから姿勢まで p50 は PyTorch＋MAGSAC 43 ms（処理 50 Hz）、
  TensorRT＋PoseLib 15 ms、いまの `live.env`（＋`RENDER=1`）18 ms（どれも処理 60 Hz 前後）。本物の Whoop ではまだ飛ばしていない
- 答えの揺れ（前後 0.25 秒の 2 次式からのずれ）は inlier で決まる：60 未満 22 cm、120〜250 で 9 cm、400 以上で 4 cm。回転の速さとは弱く（順位相関 +0.31）、
  速度とは無関係。この Whoop は回転 p50 72 °/s・p99 265 °/s で、レース機の「400 °/s 超で崩れる」領域に入らない

**精度で効かなかったこと**（クリップの真値との差 p50 は全部 7〜9 cm のまま）：飛行を地図に足す（見失いは 5 回 3.1 秒 → 3 回 1.4 秒、揺れは同じ）、
`NKF=3`・`4`、`TOPK=4096`（遅くなるだけ）、描く側の重み（inlier の 0.5 乗・1 乗・1.4 乗）と窓（0.25〜0.6 秒）と遅れ（0.1〜5 秒）。奇数・偶数フィールドのずれも無い
（平均の差 0.25 cm）。答えを 0.6 秒ぶんならしても真値との差が減らないので、残る 7 cm は隣り合う答えに共通のずれか、真値の誤差。どちらかは分けられていない。
見た目は `smooth` 0.4 秒・`delay` 0.4 秒で落ち着く（p99 84 → 61 cm）。

**ライブ用の小さな束調整（`BA=0.5`）。** 答えのたびに、直近 0.5 秒の答えをまとめて解き直す。1 つの答えは「照合点から作った 6×6 の情報行列つきの
6 自由度の測定」で、加速度と角加速度の制約でつなぐ（`BA_PX=8 BA_ACC=3 BA_ALPHA=10`。角加速度の項が Huber の閾値を超えない範囲では、効くのは比だけ）。解き直した姿勢は行の `win` に入り、
ページは届いた順に過去の答えを置き換える（`BA` のチェックで生の答えと切り替え）。`INFO=1` は情報行列を行に書く（手元で式を試す用）。

| 遅れ 0.1 秒で描いたとき | 生の答え | ページの 2 次式 | 束調整 |
|---|---|---|---|
| 揺れ p50（飛行、60 fps） | 8.0 cm | 1.14 cm | 1.0 cm |
| 揺れ p50（クリップ、25 fps） | 6.6 cm | 3.0 cm | 2.5 cm |
| 真値との差 p50 / p90 / p99（クリップ） | 8.5 / 29.9 / 94 cm | 7.4 / 24.3 / 80 cm | 6.7 / 22.1 / 52 cm |
| 向き p50 / p90（クリップ） | 1.16 / 3.68° | 生のまま | 1.00 / 2.88° |

- **効くのは遅れが短いとき、外れ値、向き。** 遅れ 0.2 秒以上なら、窓の広い 2 次式と同じ線になる（揺れ 0.3〜0.4 cm）。真値との差の中央値は 7 cm のまま
- **numpy の BLAS は 1 スレッド**（`rt_track.py` の冒頭で `OPENBLAS_NUM_THREADS=1`）。束調整の計算は 1 回 0.2 ms だが、32 コアの機械では OpenBLAS が小さな行列にも
  コア数ぶんのスレッドを立て、tracker が 54 → 33 Hz に落ちた。C で書き直す必要は無かった
- **4 人同時**（同じ録画を 4 本、束調整あり）：1 周 p50 31.9 ms、1 人 29.0 Hz、束調整の追加は 4 人で約 2 ms。揺れは遅れ 0.1 秒で 1.26 cm
- 手元の採点は win4090 の `rt/` に流した記録を持ってきて、届いた順に置き換えながら各フレームを読む（scratch の `evalwin.py`。リポジトリには入れていない）

未検証の候補は、物の縁に乗った地図の点を捨てる（このスキャンは不透明度が低く、描いた深度が縁で手前と奥の混ざりになる）、このカメラでのレンズ校正
（いまは HDZero の値）、位置の分かる目印を使った真値、本物のライブ入力で束調整を通すこと、4 人ぶんのライブ入力。

## 電池で回す（消費電力、2026-10-05）

会場に 4090 機を持ち込み、ポータブル電源（EcoFlow DELTA 2 Max、2,048 Wh）で回す場合の数字。GPU は `nvidia-smi`（200 ms ごと）、CPU はパッケージの
RAPL（Windows の `\Energy Meter(rapl_package0_pkg)\Power`、1 秒ごと）で測った。マザーボード・メモリ・ファン・電源の損失は入っていない。
録画は `PACE=1` で実時間に歩かせる。付けないと次のフレームを待たずに回し、GPU が常に埋まって電力が本番より高く出る。
測る道具は `tools/dvr/rt_power.ps1`（Windows 側で記録しつつ `rt_power_run.sh` を呼ぶ）と `rt_power_an.py`（追跡中の平均を出す）。

| 4 人同時、`RENDER=1 RCLIP=2` | GPU | CPU | 計 | d05 処理 / 遅延 p50 | レース 3 本の遅延 p50 |
|---|---|---|---|---|---|
| これまで | 188 W | 94 W | 282 W | 45 Hz / 33 ms | 37〜38 ms |
| **OpenMP 1 スレッド（いまの既定）** | 191 | 62 | 253 | 46 / 32 | 35〜37 |
| **それに GPU の電力上限 150 W** | 147 | 61 | **208** | 42 / 35 | 38〜40 |
| 上限 100 W | 100 | 78 | 177 | 29 / 46 | 58〜65（30 → 22 Hz） |
| クロック固定 2100 MHz（上限は 450） | 123 | 87 | 210 | 38 / 38 | 42〜47 |

d05 1 本（`RENDER=1`）は GPU 120 W・CPU 104 → 54 W。無負荷は GPU 22 W・CPU 31 W。答えの精度はどの行も変わらない（d05 p50 0.11〜0.12 m）。

- **CPU の大半は torch の OpenMP の空回りだった。** 16 本のスレッドが各 33% 回り、CPU は負荷に関係なく約 100 W（1 本のほうが 4 本より多い）。
  `OMP_NUM_THREADS=1` で消え、速さも精度も同じ。`rt_track.py` の冒頭で既定にした。`OPENCV_FOR_THREADS_NUM=1` は効かない
- **GPU は電力上限 150 W が手ごろ。** 200 W 以上ではほぼ下がらない（もともと平均 188 W）。100 W ではクロックが 1,200 MHz まで落ちて遅れる。

映像のあるマスが 0 / 1 / 2 / 3 / 4 の時間は 34 / 19 / 16 / 16 / 16%、GPU＋CPU の平均 131 W・1,024 Wh、壁では 190 W・1,486 Wh（84%）。配信が別の画面を映していた時間（13%）もレース中と同じだったとすると 145 W・1,608 Wh（91%）。合間の見張りは 2% しか効かない。**Event VRX の NDI は 60 fps だが、tracker が 30 fps に間引く**（`MAXFPS`、操作ページは「60 fps → 30」と出す）。間引かないと 3 マスで GPU 125 → 172 W（＋35%）、処理 43〜54 枚/秒、届いてから位置まで p50 25〜32 ms（30 fps では 19〜28 ms）。ページは 100 ms 遅らせて内挿で描くので 60 fps ぶんの答えは要らない。ここの数字は全部 30 fps。準備や片付けで映像の無い時間は 1 時間につき約 4%。

- **照合はまとめて呼ぶ。** LighterGlue は 1 組 14 ms、8 組を 1 回のバッチで 19 ms。命令を出す回数で時間が決まっている。
  バッチには点の刈り込み（`width_confidence`）を切る必要がある（B > 1 で `The size of tensor a (2048) must match the size of tensor b` で落ちる）。
  点数は TOPK にゼロ埋めし、埋めた点への対応は捨てる
- **GPU と CPU を重ねる**（`PIPE`）：d05 だけで 0 → 28 Hz、1 → 43 Hz、2 → 56 Hz。予測が 1 周古くなっても描く点は悪くならなかった（0.61 → 0.55 m）
- **PnP は PoseLib**（`PNP=poselib`、既定）。走行中の実際の入力（d05、キーフレーム 2 枚分の対応 p50 903 点、inlier 33%）で MAGSAC は 1 回 11 ms だった
  （前に測った 3 ms は 400 点の合成データ）。時間は MAGSAC の採点に掛かっていて、反復を 500 → 200 にしても 10.8 ms。PoseLib（P3P＋LO-RANSAC）は 2.8 ms で、
  答えも参照に近い（d05 p50 0.24 → 0.19 m）。GIL を手放すので 4 本のスレッドで 3.8 倍に並ぶ。**PoseLib は既定で成功確率の要る回数の 3 倍を回す**
  （`dyn_num_trials_mult` 3.0）ので 1 倍に落としてある（`PL_DYN=1`。3.8 → 2.8 ms、精度は同じ）。効かなかった：照合のスコアの順に標本を取る PROSAC（反復が減らず外れが増えた。
  LighterGlue のスコアの高さと inlier かどうかが結びついていない）、OpenCV の USAC_FAST（5 ms）。2 枚のキーフレームで同じ画素に対応した重複点（24%）を外すと 3.1 ms だが、
  答えが動くので入れていない（真値では未確認）。その前は SQPnP の RANSAC（12 ms、外れ 70% の合成データで 0/101）から MAGSAC（99/101）に替えて見失いが減った
- **照合と XFeat は TensorRT のエンジンで回す**（`GLUE=eng/glue_mix.engine XFEAT=eng/xfeat_fp32.engine`、`tools/dvr/rt_trt.py`）。tracker の形は 640×480・2048 点で
  固定なので、バッチだけ可変のエンジンにできる。TensorRT 11 は ONNX の型どおりに組む（FP16 のフラグが無い）ので、精度は書き出す型で決める。
  照合の `glue_mix`（6 層は fp16、割り当ての log-softmax と相互判定は fp32）は 8 組 19 → 10 ms、1 組 9〜13 → 3.5 ms、PyTorch との対応の一致（IoU）p50 0.92 で通しの精度は同じ。
  全部 fp16 も同じ。**fp32 のエンジンはバッチで PyTorch より遅い**（8 組 24 ms）：PyTorch 版も attention は fp16（kornia の flash の経路が `.half()` する）。
  XFeat は detectAndCompute の可変長の段（NMS の `nonzero`、候補の `argsort`）を「全画素の点数（落ちた画素は -1）から topk」にして固定した（点の一致 IoU 0.99、記述子のコサイン 1.000）。
  本体の短縮は 4 枚 4.3 → 2.7 ms と小さく、効くのは点を 2048 の固定長のまま有効マスクつきで照合へ渡すこと：フレームごとの切り出し（1 枚ごとに GPU を待つ）と
  照合前の詰め直しが消える（照合は点の順序に依存しないので、マスクした点をゼロにして対応を捨てれば同じ）。照合の結果も組ごとでなく 1 回で CPU に移す。
  XFeat の fp16 は速くならない（チャンネルの少ない畳み込み）。書き出しで直したもの：kornia の `unflatten(-1, (heads, -1, 3))`（TensorRT が読めない）と `repeat_interleave`
  （形を証明できない）は posenc と attention を定数の形で書き直し、XFeat の `BatchNorm2d(affine=False)` は 1 と 0 の重みを明示（書き出しが CPU に重みを作って
  `Expected all tensors to be on the same device` で落ちる）。比較の記録は win4090 の `rt/trt/`（出力 `rt/trt/out/`、`rt/trt/office/`）
- **LighterGlue の PyTorch の fp16（`mp`）は使わない。** 解けるフレームが 1,630 → 761 に減り、速くもならない。悪いのは autocast のほうで、TensorRT の fp16 は上のとおり問題ない
- **見失いは時間で数える。** 試した回数で数えると、速くするほど短い時間で諦め、重い再局在化（約 100 ms、その間フレームが落ちる）
  に入ってまた見失う。fp16 と重なって、原因を取り違えかけた
- **描く点のギザギザは答えそのものの揺れ**（1 つ 0.25 m）。外挿の速さを最近の速さで抑えても変わらなかった。カルマン＋段差を溶かすと
  0.86 → 0.70 m、揺れ 18 → 11 cm。それ以上は軌跡を遅らせて描き直すほうが効く
- 効かなかった：予測姿勢で対応を先に絞る、OpenCV のスレッド数。特徴点 512 は減らしすぎ（Mac で見失いが増えた）。
  特徴点 1,024・キーフレーム 1 枚は Mac では効いた（上）。4090 で最初に測ったときは fp16 が入ったままだったので、4090 での答えはまだ無い
